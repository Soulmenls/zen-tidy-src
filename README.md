# Zen Tidy

Zen Tidy is a Firefox WebExtension for [Zen Browser](https://zen-browser.app). It sorts your loose tabs into topic
groups with Claude, using your own Anthropic API key.

1. Click the Zen Tidy toolbar button.
2. It sends your loose tabs to Claude (`claude-sonnet-5-5` by default): title, site and a short path. Tabs that look
   sensitive send only the site. Then `claude-haiku-5-5` checks each larger group on its own and splits any that mixes
   subjects; how far it goes is the **Precision** setting, from 1 (no check, the most tabs grouped) to 5 (the
   default: one subject per group, a tab with nothing like it left ungrouped).
3. You get a **preview** of the groups. Rename them, change their icons, move or untick tabs.
4. **Apply** moves the tabs into unpinned tab groups. **Undo** puts them back, even after a restart.

Nothing runs unless you click. Essentials, pinned tabs, Zen folders and split views are never moved. The key is sent
only to `https://api.anthropic.com`.

Target: Zen 1.24b (Firefox 159) on Windows.

## Install

Releases are published at [github.com/Soulmenls/zen-tidy](https://github.com/Soulmenls/zen-tidy/releases), signed
by Mozilla (unlisted, so not on addons.mozilla.org).

1. From the [latest release](https://github.com/Soulmenls/zen-tidy/releases/latest), download
   `zen-tidy-<version>.xpi`. To check it, compare
   `(Get-FileHash .\zen-tidy-<version>.xpi -Algorithm SHA256).Hash` with its line in the release's `SHA256SUMS`
   (the case of the letters doesn't matter).
2. In Zen, open `about:addons`, click the gear, choose **Install Add-on From File…** and pick the `.xpi`. Zen shows
   the permissions it asks for; confirm with **Add**.
3. Settings opens on its own: paste your Anthropic API key, click **Save**, then **Test key**. Use a key from a
   workspace of its own with a low monthly spend limit.
4. For the folder look, see the next section.

**Updates** arrive on their own: Zen checks the latest release's `updates.json` in the background (Firefox's default
is once a day), installs the new version and keeps your key, settings, Undo and collapsed groups. An update that
comes while Zen Tidy is tidying, applying or undoing waits until that is done, and one that comes while a preview
waits for you waits until you apply or cancel it (Zen's next start installs it in any case). An update keeps no
finished tidy's summary: the popup opens fresh, with Undo still offered. When a release changes the CSS, its notes
say to run `setup-css.ps1` again.

**Remove it:** "Remove all tidy groups" in the groups view if you want your tabs loose again, then remove Zen Tidy in
`about:addons` (that deletes its key and settings), then uninstall the folder look as below.

Never turn off signature checks (`xpinstall.signatures.required`) in your real profile.

## Folder look (optional)

Tidy groups are plain Firefox tab groups. A small stylesheet, `css/zen-tidy.css` (generated by
`scripts/gen-css.mjs`), makes them look and behave like Zen folders:

- each group shows the Zen folder icon it was given;
- collapsing a group hides its tabs, except the selected one;
- the label and the tab indent follow Zen's folder style.

Zen loads it through the profile's `userChrome.css`. `scripts/setup-css.ps1` sets that up in one profile, and takes
it out again. It works in Windows PowerShell 5.1 and PowerShell 7.

The packaged extension contains neither the script nor the CSS. Each release carries them as
`zen-tidy-css-<version>.zip`: unzip it and run the commands below from the unzipped folder (the one that holds
`scripts\` and `css\`). A clone of this repository has the same layout.

**Install**

1. Find your profile folder: in Zen, open `about:support` and look at **Profile Folder**.
2. **Close Zen.** The script refuses while that profile is open (other profiles may stay open). While it runs, it
   holds the profile's lock as Zen does, so Zen can't start on that profile until it has finished.
3. See what it would change, without writing anything:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-css.ps1 -ProfilePath "C:\Users\you\AppData\Roaming\zen\Profiles\abcd1234.Default (release)" -WhatIf
   ```

4. Run it again without `-WhatIf`, then start Zen.

It then:

- copies `css\zen-tidy.css` to `chrome\zen-tidy.css` in the profile. If a `chrome\zen-tidy.css` of your own is
  already there (one without the generated `/* Zen Tidy:` header), it is backed up first, and the uninstall puts it
  back;
- adds `@import "zen-tidy.css"; /* zen-tidy */` as the first rule of `chrome\userChrome.css`, creating the file if
  needed. Everything else in the file is kept byte for byte (encoding, BOM, line endings);
- adds `user_pref("toolkit.legacyUserProfileCustomizations.stylesheets", true); // zen-tidy` to `user.js`, because
  Zen loads no `userChrome.css` without it. If your `user.js` sets it to false, you get a warning and this line
  overrides it;
- backs up `userChrome.css` and `user.js` before changing them, as `<name>.zen-tidy-backup-<yyyyMMdd-HHmmss>`, and
  never overwrites an earlier backup;
- records what it found in `chrome\zen-tidy.install.json`, so the uninstall can put it back.

Each file is written to a temporary file next to it, which then takes the old file's place in one step. If a write
fails (another program holds the file, the disk is full), the file stays exactly as it was.

It is safe to run again, for example after an update that changes the CSS: it only changes what is out of date, and
says "nothing to do" otherwise.

It refuses a `chrome\` folder, `userChrome.css` or `user.js` that is a junction, a symbolic link or a hard link, such
as a theme folder or a `user.js` shared by several profiles (a common arkenfox setup): its changes, and the record of
what it found, would reach every profile that shares it. Replace the link with the profile's own copy first.

With `-Confirm` it asks before each step. If you decline one, it skips what depends on it, says the run was only
partly done, and a later run finishes the job.

**Uninstall**

Close Zen, then:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-css.ps1 -ProfilePath "C:\Users\you\AppData\Roaming\zen\Profiles\abcd1234.Default (release)" -Uninstall
```

It removes exactly what the install added: the `@import` line, the `user.js` line, `zen-tidy.css` (your own is put
back, if the install replaced one) and `install.json`. Files it created are deleted once nothing else is in them, and
the backups are kept. Zen may keep the stylesheet pref switched on in `prefs.js`, which is harmless; you can reset it
in `about:config`.

**Exit codes:** 0 done (or nothing to do, or partly done because you declined a `-Confirm` step), 1 unexpected error,
or an argument PowerShell itself rejects before the script starts (a switch given a value, such as
`-Uninstall:$false`, or a parameter with no value), 2 bad arguments (no `-ProfilePath`, or one it doesn't know) or no
CSS to copy, 3 not a profile folder, 4 the profile is open in Zen (or the script is already running on it), 5 a file
it would edit is in a form it can't edit safely (such as UTF-16), is read-only, or is a link. On a refusal it writes
nothing.

## Development

```powershell
npm test            # unit tests, under a memory cap and a time limit
npm run tools       # once per clone, and whenever tools/web-ext/package-lock.json changes: installs the pinned web-ext
npm run lint:ext    # web-ext lint of extension/, with the pinned web-ext (WEB_EXT_* variables are ignored: pass flags)
npm run hooks       # once per clone: turns on the pre-commit check
npm run test:update # the auto-update test in a throwaway Zen profile (local update server, unsigned builds)
```

**Pre-commit check.** `npm run hooks` (`scripts/install-hooks.mjs`) copies `scripts/git-hooks/pre-commit` into the
repository's own hooks folder (`.git/hooks/`), which every branch and every linked worktree shares, and unsets the
`core.hooksPath` an earlier version of it set. It refuses, changing nothing, when another pre-commit hook is already
there or another `core.hooksPath` would make git skip it. Before each commit, the hook runs that checkout's
`scripts/precommit-check.mjs`, which reads the staged content (not the working tree) and refuses the commit, naming
the file and line, when it holds:

- an Anthropic key-shaped string. A fake key in a tracked file passes only with `VDfake`, `TEST` or `EXAMPLE` as
  one of its dash- or underscore-separated parts;
- an AMO JWT secret (64 hex characters on a line that names a JWT or secret), or a JWT issuer next to one;
- a file named `fixtures/real-*`, `*.env`, `.env*`, `amo-credentials.xml`, `*.pfx` or `*.p12`;
- anything under `test/`, `notes/` or `.omc/`, or `SPEC.md`: they are git-ignored, and this catches `git add -f`;
- an export from `export-tabs.mjs`, or a Zen session file (`*.jsonlz4`, or the mozLz4 header under any name).

It prints at most the first 8 characters of what it found. Take the file out of the commit
(`git restore --staged <file>`), remove the secret, and commit again.

A checkout without `scripts/precommit-check.mjs` (a branch from before the check, such as `main` before it was merged,
or a worktree of an older commit) refuses every commit, rather than letting it through unchecked. Commit there only
deliberately, with `git commit --no-verify`.

## Releasing

Releases are built and signed on this PC only, then published to the public, releases-only repository
`Soulmenls/zen-tidy`: a README and the release assets. The source is public at `Soulmenls/zen-tidy-src`; the notes
and tests stay on this PC. Zen looks for
updates at `https://github.com/Soulmenls/zen-tidy/releases/latest/download/updates.json` (the manifest's
`update_url`), so the newest release must always be the one marked latest.

**Once**

- 2FA on the GitHub account and on the Mozilla add-ons account.
- `Soulmenls/zen-tidy` is public, has a default branch, has **immutable releases** turned on and a tag ruleset that
  protects `v*` from updates and deletion.
- `gh auth login`. The token stays in the keyring; the release script never reads or prints it.
- `npm run tools` installs the pinned web-ext 10.7.0 into `tools/web-ext/node_modules/` (git-ignored): `npm ci
  --ignore-scripts` from the committed `tools/web-ext/package-lock.json`, so every package below web-ext is the exact
  registry.npmjs.org tarball and sha512 hash the lockfile names, and no package runs code at install. It is the only
  step that reaches the network for web-ext. Run it again whenever that lockfile changes: `check` refuses a missing or
  stale install and says so.
- Store the AMO API key once: `pwsh -ExecutionPolicy Bypass -File .\scripts\amo-credentials.ps1`, in a terminal, asks
  for the JWT issuer and secret (addons.mozilla.org, Developer Hub > Manage API Keys) and a passphrase of at least 12
  characters, and saves the key to `%LOCALAPPDATA%\zen-tidy-dev\amo-credentials.xml`, locked with that passphrase and
  Windows DPAPI: only your Windows account on this PC, given the passphrase, can unlock it. It stays there between
  releases. `-Check` says whether it is stored and locked, `-Test` whether a passphrase unlocks it; to change the
  passphrase, store the key again.

**Each release** (version `X.Y.Z`: digits only, higher than every earlier release)

1. `node scripts/release.mjs bump X.Y.Z` writes the version into `extension/manifest.json` and `package.json`,
   nothing else. Commit that.
2. `node scripts/release.mjs check`: the preflight, offline, writing nothing outside `dist/`. It wants a clean tree,
   a new version, the manifest guards (product id, `update_url`, exact permissions and CSP, none of the keys that
   open the extension to web pages), `API_BASE` set to `https://api.anthropic.com`, no test or dev file and no
   key-shaped string in `extension/`, the pinned web-ext installed exactly as its lockfile says, `npm test` passing
   and `web-ext lint` without errors.
3. `node scripts/release.mjs build --notes <file>` copies the committed `extension/` (HEAD's files, byte for byte,
   whatever line endings git gave the working tree) into `dist/release/X.Y.Z/`, lints it, and writes the unsigned
   zip, a draft `updates.json`, `SHA256SUMS`, `RELEASE-NOTES.md` (with the user-facing changes from `<file>`) and the
   CSS kit, also from HEAD. Read the notes.
4. If the AMO key isn't stored yet (`scripts\amo-credentials.ps1 -Check` says so), store it as under **Once**.
5. `node scripts/release.mjs sign --confirm X.Y.Z --notes <file>` **uploads to Mozilla**. It builds again (same
   notes file), then `scripts\sign.ps1` asks for the key's passphrase in a Windows dialog (three tries; Cancel, or
   five minutes without an answer, stops it before anything is sent), signs the staged folder on the unlisted channel,
   checks the signed xpi offline against the staged files (byte for byte, except `manifest.json`: AMO writes it out
   again, so it must parse to the same value), and finishes `updates.json`, `SHA256SUMS` and the notes with the
   signed xpi's hash. The dialog works however `release.mjs` was started, by a tool with no console input too.
6. Leave the key stored: it stays locked between releases. Revoke it on addons.mozilla.org (Developer Hub > Manage
   API Keys) and run `scripts\amo-credentials.ps1 -Remove` only if this PC or the passphrase may be compromised, or
   when you retire this PC.
7. `node scripts/release.mjs publish --confirm X.Y.Z` **uploads to GitHub**. It checks the repository's settings,
   creates the release `vX.Y.Z` as a draft, uploads the xpi, `updates.json`, the CSS kit and `SHA256SUMS`,
   downloads them back to compare their hashes, and publishes the draft as latest. At once it records the release in
   `%LOCALAPPDATA%\zen-tidy-dev\releases.json` and tags the source commit `vX.Y.Z` locally (it pushes nothing to
   `Soulmenls/zen-tidy-src`); then it checks that GitHub marks the release immutable and that the latest
   `updates.json` names X.Y.Z.

`--confirm` must repeat the manifest's version, so an upload can't start by accident or for the wrong version.

The release only ships what git can vouch for: `check` refuses a file marked assume-unchanged or skip-worktree (git
status hides changes to it; `git update-index --no-assume-unchanged --no-skip-worktree <file>` clears the mark), and
every file it packages is read from the commit. The commands it starts (npm, web-ext, `sign.ps1`, gh) never see a
`WEB_EXT_*` variable, `NODE_PATH` or a GitHub token or host (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_HOST` and the enterprise
ones) from your shell, so gh always uses its keyring login; `sign.ps1` doesn't get `NODE_OPTIONS` either, and clears
the same variables itself when you start it by hand. The lint and `sign.ps1` run the same pinned web-ext from
`tools/web-ext/` with the same node, the one running `release.mjs` (`sign.ps1` refuses before it asks for the
passphrase when either is missing or web-ext is another version), and nothing is installed or resolved by version
range on the way. The lockfile may only name registry.npmjs.org tarballs, each with one sha512 hash: no git, file,
link or URL dependency, and no optional package npm could leave out. `check` runs these rules and compares the
installed tree with the lockfile (npm's own record of what it installed, and each package's `package.json` on disk),
and `sign` does both again right before the upload.

**When a step fails** it stops with one line naming the rule or the step.

- `check` or `build`: fix what it names, commit, and run it again. Nothing has left this PC.
- `sign`: run the same command again. A signed xpi for this version already in `dist/release/X.Y.Z/signed/` that
  verifies is used without uploading anything. Otherwise web-ext reuses its earlier upload of the unchanged package
  (it keeps the upload's id in the stage, `.amo-upload-uuid`) instead of sending the file again, but it still submits
  the version, and Mozilla never accepts the same version twice. So after a timeout while Mozilla was reviewing it,
  download the signed file from the version's page on addons.mozilla.org into `dist/release/X.Y.Z/signed/` and run
  `sign` again. If Mozilla rejected the version, fix the cause and release the next patch version.
- `publish`, before the draft is published: only a draft exists. Delete it on GitHub and run `publish` again.
- `publish`, after the draft is published: the release is immutable, and already recorded and tagged, even if
  `publish` stopped during its last checks. Never delete it (its tag could not be used again). What to do depends on
  the last line:
  - "could not be confirmed yet": a request failed, or GitHub had not shown the release immutable yet. Nothing is
    known to be wrong. Run `node scripts/release.mjs verify --confirm X.Y.Z` a minute later: it reads the release and
    the update URL again (it changes nothing on GitHub) and records the release as verified once they check out.
  - "only the local tag is missing": run the `git tag` command it prints.
  - anything else (another file or version at the update URL): ship the fix as a new patch version.
- If `publish` reports a `vX.Y.Z` already published that this PC has no record of (a run stopped between GitHub
  publishing it and the ledger write), open `%LOCALAPPDATA%\zen-tidy-dev\releases.json` and change the `X.Y.Z`
  entry's `"state"` from `"signed"` to `"published"`, keeping every other field (that entry already holds the
  hashes and the commit the ledger needs). Then run `git tag vX.Y.Z <that entry's commit>` and
  `node scripts/release.mjs verify --confirm X.Y.Z`. The error prints both commands.
